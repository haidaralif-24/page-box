# 2026-11-19 - v0.4 storage: real files vs. pure SQLite

## What I did
- First attempt: **real directory storage**. Collections became actual folders
  (`workspace/Projects/`), pages became slugified `.html` files
  (`my-awesome-page.html`), renames/moves physically moved files on disk
  (version history files included), with an automatic migration from the old
  `pages/<uuid>/` layout.
- Then reverted the whole thing to **pure SQLite virtual directories**:
  collections are rows with `parent_id`, page HTML lives in a `content`
  column, and the "folders" only exist in the tree-view sidebar
  (expand/collapse included).
- Removed `fileName` / `relPath` from the frontend interfaces and the browser
  mock so no file-system concepts leak into the UI.
- Added a migration for existing databases missing the new `content` column.

## What went wrong
- The real-files approach ran into macOS permission errors — that's what
  pushed the revert. Writing and moving files around under app-data is
  exactly the kind of thing that behaves differently on every machine.
- Reverting took several passes (backend storage first, frontend types
  after), plus a `backup` commit and two pull-merges to reconcile parallel
  work before the tree view landed cleanly.
- Databases created by the intermediate builds didn't have the `content`
  column, so startup broke until the migration landed. Empty-content rows
  needed a separate backfill (next entry).

## What I learned
- One source of truth beats two. Syncing SQLite metadata with files on disk
  means every rename/move/delete can half-fail; a virtual tree gives the same
  UX with transactions instead of file I/O.
- "Looks like folders" is a UI concern, not a storage concern.
- Every schema change needs a migration path from *every* version that ever
  ran on my machine, not just the last one.

## Next
